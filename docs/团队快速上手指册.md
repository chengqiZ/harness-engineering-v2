# AI Coding Harness 团队快速上手指册（v2）

> 本手册面向业务仓库开发团队成员。
> 你只需要做三件事：① 把规范源库接入你的业务仓库；② 用 `./ai` 走机械步骤；③ 让你的 AI 工具（任何家都行）读取 skills 执行开发。
> 完整流程规范、方案对比和验收标准详见 [docs/业务仓库接入与执行SOP.md](业务仓库接入与执行SOP.md)。

---

## v2 和 v1 有什么不一样（老用户看这段）

| 事项 | v1 | v2 |
|---|---|---|
| `./ai` 干什么 | 调度 Codex 执行任务 | 只做机械操作（建骨架、切分支、跑门禁、提交），不调度任何 AI |
| 谁执行开发 | 只有 Codex 走自动化，其他工具手动复制提示词 | 任何宿主 agent（Claude Code、Codex、OpenClaw、Gemini CLI 等）读同一套 skills，完全平等 |
| 提示词模板 | 6 个模板 + 4 个渲染脚本 | 4 个 SKILL.md（spec-prep / task-dev / pr-prep / serial-task），`./ai skill <name>` 取路径 |
| 验收 | 人工打勾 | 每个 task 写 `Validation Command:`，`./ai done` 逐条执行，全过才提交 |
| 新增命令 | — | `./ai done`（门禁+提交）、`./ai resume`（断点恢复）、`./ai skill` |

spec 四件套格式、task 卡片、S/M/L 分级、单 PR 单 task、submodule 版本锁定全部不变；你的存量 spec 直接可用。

## 第一步：接入规范源库

在业务仓库根目录执行一条命令，完成所有初始化。

### 1.1 前置条件

- 业务仓库已初始化 git（根目录有 `.git`）
- 本机已 clone 规范源库（脚本需要读取本地文件来运行 bootstrap）

```bash
# 先 clone 规范源库到你的工作区（只需一次）
cd ~/workspace
git clone https://github.com/chengqiZ/harness-engineering-v2.git
```

### 1.2 执行初始化

```bash
# 进入业务仓库根目录
cd ~/workspace/my-business-repo

# 执行接入脚本，参数是规范源库的 GitHub 地址
bash ~/workspace/harness-engineering-v2/scripts/init_business_repo.sh https://github.com/chengqiZ/harness-engineering-v2.git
```

### 1.3 验证接入成功

```bash
./ai status
```

看到以下输出即表示接入成功：

```
repo: my-business-repo
branch: main
standards: .ai-harness/.ai-standards (xxxxxxx)
specs:
none
```

### 1.4 提交初始化结果

```bash
git add .gitmodules .ai-harness .github ai
git commit -m "chore(harness): 接入 AI Coding Harness v2"
```

接入后业务仓库会新增以下内容：

| 路径 | 说明 |
|---|---|
| `.ai-harness/.ai-standards/` | 规范源库 submodule（锁定版本，只读） |
| `.ai-harness/AGENTS.md` | 项目特例文件（你只写本项目与标准不同的地方） |
| `.ai-harness/specs/` | 需求 spec 目录（每个需求一个子目录，含原始需求文档 source.md） |
| `.ai-harness/docs/changelog/` | 变更记录 |
| `.ai-harness/pr/` | MR 材料文件 |
| `.github/pull_request_template.md` | PR 模板 |
| `./ai` | 日常命令入口（机械操作，任何 AI 工具通用） |

## 第二步：机械步骤 + 让 AI 读 skills

> **核心思路**：`./ai` 负责确定性操作，你的 AI 工具负责需要动脑的操作。两者用同一套流程，换工具不用换流程。

### 2.1 整体流程图

```
需求文档 → ./ai spec（骨架+拷入文档） → AI 读 spec-prep skill 补齐四件套 → 你确认
→ ./ai work（切分支） → AI 读 task-dev skill 开发+验证 → ./ai done（门禁+提交）
→ AI 读 pr-prep skill 写 MR 描述 → ./ai pr（推送+MR材料） → 平台建 MR
```

### 2.2 阶段一：新需求 → 生成 spec

**准备需求文档**（任意格式，PRD、方案说明、缺陷描述都可以）：

```bash
mkdir -p docs/requirements
# 把需求文档放到这里，例如 docs/requirements/login-page.md
```

**跑机械命令**（自动建四件套骨架 + 把需求文档拷进 spec 目录）：

```bash
./ai spec login-page docs/requirements/login-page.md
```

**对你的 AI 工具说**：

```text
请读取 ./ai skill spec-prep 指向的 SKILL.md，
基于 .ai-harness/specs/login-page/source.md 补齐四件套。
要求每个 task 在 04-acceptance.md 写至少一条 Validation Command。
完成后输出：每个文件的完成摘要、Open Questions、推荐的第一个 ready task。
```

AI 会输出四个文件到 `.ai-harness/specs/login-page/`：
- `01-requirements.md` — 需求梳理
- `02-design.md` — 设计方案
- `03-tasks.md` — 任务拆解（含 Task ID、复杂度、依赖）
- `04-acceptance.md` — 验收标准（**含每个 task 的 Validation Command**）

**你确认**：检查 spec 四件套，确认需求和任务拆解合理后，再进入开发。

### 2.3 阶段二：开发单个 task

**切任务分支**（脏区自动 stash，不用先清理工作区）：

```bash
./ai next login-page        # 看下一个该做哪个 task
./ai work login-page T1     # 切到 feat/login-page-T1 分支
```

**对你的 AI 工具说**：

```text
请读取 ./ai skill task-dev 指向的 SKILL.md，执行 T1。
完成后运行 T1 的 Validation Command 并更新 04-acceptance.md，
然后停止等我评审；不要自行调用 ./ai done。
```

AI 会：只实现 T1、行为变化补测试、补注释、更新 `04-acceptance.md` 记录证据，然后停下。

**你评审**：检查代码和测试证据。

**跑门禁并提交**：

```bash
./ai done login-page T1
```

`./ai done` 会逐条执行 T1 的 Validation Command，全过才本地提交；失败会打印输出尾部，修好再跑。

### 2.4 阶段三：准备 PR

**对你的 AI 工具说**：

```text
请读取 ./ai skill pr-prep 指向的 SKILL.md，为 T1 生成 MR 描述。
```

**推送并落 MR 材料**：

```bash
./ai pr login-page T1 main
```

会生成 `.ai-harness/pr/login-page-T1-mr.md` 并推送分支（提交/推送前有人工确认门）。

**你确认**：检查 PR 材料，确认后在平台创建 MR。

### 2.5 一键串行执行（推荐给熟练成员）

低风险 S 级需求，从头到尾一口气走完（骨架 → AI 补 spec → 首个 task）：

```bash
./ai run login-page docs/requirements/login-page.md
```

中断了就：

```bash
./ai resume login-page
```

按输出的 Resume Command 继续。

想连续执行多个 task，对你的 AI 工具说：

```text
请读取 ./ai skill serial-task 指向的 SKILL.md。
按 .ai-harness/specs/login-page/03-tasks.md 依赖顺序串行执行 task，
每个 task 走 ./ai work → task-dev skill → ./ai done 闭环，
每完成一个 task 暂停等我确认。
```

## 第三步：团队其他成员 clone 后怎么用

新成员 clone 了业务仓库后，只需拉取 submodule：

```bash
cd ~/workspace/my-business-repo
git submodule update --init --recursive
```

然后 `./ai status` 验证可用，即可按第二步的流程使用。

## 底线规则（让 AI 遵守）

skills 里已经写好了，但你需要知道：

| 规则 | 说明 |
|---|---|
| 一个 task 一个 PR | 不要把多个 task 混在一起 |
| spec 阶段写好 Validation Command | 「什么算验收通过」在开发前对齐，不是开发后打勾 |
| 行为变化补测试 | bug 修复加回归测试 |
| 注释覆盖关键点 | 类/模块、方法、条件分支、边界、风险逻辑 |
| 高风险必须暂停 | DB migration、权限、计费、认证 → AI 会停下来问你 |
| 每个 task 完成后暂停 | AI 输出验证结果后等你确认才继续 |

## 排错速查

| 问题 | 解决方式 |
|---|---|
| `./ai` 报错找不到 standards | `git submodule update --init --recursive` |
| AI 没读规范 | 第一条消息加上：\"请先读取 .ai-harness/.ai-standards/AGENTS.md 和 standards/*.md\" |
| AI 一次做了多个 task | 立即叫停，`git checkout` 回退到上一个 commit |
| 门禁命令本机跑不了 | 把阻塞原因写进 `04-acceptance.md`，人工评审决定放行与否 |
| 规范升级后出问题 | `bash .ai-harness/.ai-standards/scripts/update_business_standards.sh <旧tag>` 回退 |
| 项目特例怎么写 | 写到 `.ai-harness/AGENTS.md`，每条带 `Reason / Scope / Expiry` |
